# SPDX and Data Model

## SPDX versions in play

- `sbom-tool generate` itself always produces **SPDX 2.2** JSON (`MANIFEST_VERSION = '2.2'` in
  `task/utils/sbomTool.ts`), written to `_manifest/spdx_2.2/manifest.spdx.json`.
- If `fetchSecurityAdvisories` finds any advisories, `addSpdxPackageSecurityAdvisoryExternalRefsAsync`
  (`task/utils/spdx/addSpdxPackageSecurityAdvisories.ts`) bumps `sbom.spdxVersion` in-place to
  **SPDX 2.3** — that's the minimum SPDX version whose `externalRefs` shape supports a
  `SECURITY`/`advisory` category/type pair. If no advisories are found, the file stays 2.2.
- All of this repo's own **model types** (`shared/spdx/models/2.3/*.ts`) are written against 2.3,
  used as the working representation for both post-processing (task side) and rendering (UI side)
  regardless of which literal `spdxVersion` string ends up in the JSON. `document.ts` exports
  `DocumentVersion.SPDX_2_3` and helpers like `getDisplayNameForDocument`, `isPackageRootLevel`.
- The UI also understands an **older/legacy** security-advisory encoding via
  `shared/spdx/parseSpdxLegacySecurityAdvisories.ts` (used as a fallback in
  `ui/components/sbom/documentPage.tsx` when the new-style `externalRefs`-based advisory isn't
  found) — keep this in mind if you ever change how advisories are attached to a package; both
  encodings currently need to keep working for manifests generated by older task versions.

## Multi-manifest merge (`shared/spdx/mergeSpdxDocuments.ts`)

Used by the UI (see [UI Report Tab](UI-Report-Tab.md)) when a build produced more than one SBOM.
`mergeSpdxDocuments(packageName, packageVersion, sourceDocuments)`:

1. Renames each document's `SPDXRef-RootPackage` to a unique id
   (`SPDXRef-Package-{sanitizedName}-{uuid}`) — every source doc has a root package with the _same_
   id, so this avoids collisions once concatenated. Renaming also patches every relationship /
   `documentDescribes` entry that pointed at the old id.
2. Renames files similarly, prefixing each file's id with its owning package name (or an MD5 hash of
   the source document's namespace if the file isn't in any package's `hasFiles`), again patching
   references.
3. Concatenates `files`/`packages` (de-duped by `SPDXID`)/`externalDocumentRefs`/`relationships`/
   `documentDescribes` across all source documents.
4. Produces a new `documentNamespace` (`{scheme}://{host}/{packageName}/{packageVersion}/{new-guid}`,
   host taken from the _first_ source document's namespace) and a fresh `creationInfo` (creator
   organization inherited from the first source document, tool creator hardcoded to
   `rhyskoedijk/sbom-azure-devops`).
5. Always stamps `spdxVersion: SPDX_2_3` on the result, regardless of the source documents'
   versions.

This is a pure, synchronous, in-repo function — no I/O — so it's straightforward to unit test if
you extend it.

## GitHub Advisory (GHSA) enrichment

- `shared/ghsa/client.ts` — `GitHubGraphClient`, a thin wrapper over the
  [GitHub GraphQL API](https://docs.github.com/en/graphql)'s `securityVulnerabilities` query.
  Queries are **per package name**, batched 100-at-a-time in parallel
  (`batchGraphQueryAsync`) since the API doesn't support querying many packages in one request;
  a failed batch logs a warning and is skipped rather than failing the whole run (data may end up
  incomplete, not absent).
- After fetching, results are filtered to (a) non-withdrawn advisories and (b) advisories whose
  `vulnerableVersionRange` (comma-separated clauses like `>= 4.3.0, < 4.3.5`) is actually satisfied
  by the installed package version, via `semver.satisfies`.
- `task/utils/spdx/addSpdxPackageSecurityAdvisories.ts` is the caller: it groups SPDX packages by
  ecosystem (derived from each package's `PackageManager` external ref's PURL —
  `getGhsaEcosystemFromPackageUrl`, which maps PURL types like `golang`/`pypi`/`gem`/`cargo` to
  GHSA's ecosystem enum names `GO`/`PIP`/`RUBYGEMS`/`RUST`, and passes the rest through uppercased),
  queries GHSA per ecosystem, then for every matched vulnerability appends **two** external refs to
  the affected package:
  1. `Security/Advisory` — human-readable, `referenceLocator` = the advisory's permalink,
     `comment` = `[{severity}] {summary}; Affects {name} v{version}`.
  2. `Security/Url` — machine-readable, `referenceLocator` = a `data:text/json;base64,...` URI
     encoding the **entire** `ISecurityVulnerability` object. This is what the UI actually parses
     back out (see `parseExternalRefsAs` usage in `documentPage.tsx`) to render advisory detail —
     the human-readable ref is there for anyone reading the raw SPDX JSON directly.
- Ecosystem support is intentionally partial — `getGhsaEcosystemFromPackageUrl` returns `undefined`
  (silently skipping advisory lookup for that package) for any PURL type it doesn't recognize.
  Extend the `switch` there if `sbom-tool`/Component Detector starts reporting a package manager
  this list doesn't cover yet.

## `vulnerabilitiesSource` (file-based vulnerability enrichment)

An alternative/supplement to GHSA fetching, for when the GitHub connection can't be used (e.g.
`InstallationToken` auth — see [Troubleshooting](Troubleshooting.md)) or vulnerability data comes
from another scanner. Implemented in
`task/utils/spdx/addSpdxPackageVulnerabilitiesFromFile.ts` (`addSpdxPackageVulnerabilitiesFromFileAsync`):

- Reads one or more JSON files (paths resolved from the `vulnerabilitiesSource` task input), each a
  flat array of `IExternalVulnerability` (`shared/ghsa/models/externalVulnerability.ts`) — a
  hand-generatable shape, unlike `ISecurityVulnerability` which mirrors GHSA's own GraphQL response.
- Matches each entry to SBOM packages by `name` (case-insensitive) and, if `packageVersion` is set,
  `versionInfo` — there's no purl/ecosystem grouping like the GHSA path, since there's no external
  API call to batch.
- Converts each match to an `ISecurityVulnerability` (deriving a `permalink` from `cveId`/a
  `GHSA-*` `id` when no `url` is given, so the entry still dedupes correctly by permalink in
  `documentPage.tsx`) and calls the **same** `addSecurityAdvisoryExternalRefsToPackage` helper the
  GHSA path uses — so both paths write identical external-ref shapes and the UI can't tell them
  apart. See [Task Reference § `vulnerabilitiesSource` format](Task-Reference.md#vulnerabilitiessource-format)
  for the full field list.
- Also bumps `sbom.spdxVersion` to 2.3 when it applies at least one vulnerability, same as the GHSA
  path.

## XLSX and SVG generation

- **XLSX** (`shared/spdx/convertSpdxToXlsx.ts`, `convertSpdxToXlsxAsync`) — builds a workbook via
  `json-as-xlsx`, runs in the **task** (Node) at generate time. This is the only one of the two
  optional exports that has a unit test.
- **SVG** (`task/utils/spdx/convertSpdxToSvg.ts`, `convertSpdxToSvgAsync`) — builds a directed graph
  with `@vizdom/vizdom-ts-node` (a Rust/WASM graph-layout library) and exports it as SVG text.
  Notable implementation details:
  - Requires a `globalThis.crypto` shim (`node:crypto`'s `webcrypto`) applied **before** importing
    vizdom, because vizdom's Rust `getrandom` dependency doesn't support Node ESM natively.
  - Builds one vertex for the document root, one per package, and one per external reference that's
    a security advisory (colored by severity: critical/high/moderate/low, shaped as a diamond,
    clickable via the advisory permalink) — `PackageManager`-category external refs are skipped
    entirely (`continue` in the switch). **Individual files are deliberately excluded** from the
    graph: on a real-world manifest, files vastly outnumber packages (e.g. 130k files vs. 2.2k
    packages) and graphing them made the SVG both slow to generate and unreadable once rendered.
    Package-to-package (and package-to-advisory) edges, built directly from `spdx.relationships`,
    are still fully represented.
  - There's a `TODO` in the code to eventually move this rendering into the browser instead of the
    agent — today the "Relationship View" tab in the UI just displays this pre-rendered SVG with
    pan/zoom (`react-zoom-pan-pinch`), it does not lay out the graph itself.
