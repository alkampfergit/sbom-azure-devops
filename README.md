# SBOM Tool Azure DevOps Extension

Unofficial Azure DevOps extension for [microsoft/sbom-tool](https://github.com/microsoft/sbom-tool). Sbom-tool runs locally on your pipeline agent without the need for subscriptions, account sign-ups, or shipping your data to a third-party service; All generated manifest files are published directly to your build artifacts and can be viewed in a human-friendly format from the "SBOM" build result tab.

Check referenced packages for known vulnerabilities against the [GitHub Advisory Database](https://github.com/advisories).

![example.build.tab.security.png](images/example.build.tab.security.png)

View referenced packages, including the package manager, type, dependency hierarchy, license, supplier, and vulnerability counts:

![example.build.tab.packages.png](images/example.build.tab.packages.png)

View manifest relationships as a network graph or export to SVG.

Export manifest objects to XLSX workbook.

![example.manifest.spdx.xlsx.png](images/example.manifest.spdx.xlsx.png)

## Install

Install the extension from the [Visual Studio marketplace](https://marketplace.visualstudio.com/items?itemName=rhyskoedijk.sbom-tool).

## Usage

In YAML pipelines:

```yaml
jobs:
  - job: publish
    steps:
      - task: DotNetCoreCLI@2
        displayName: 'Publish project'
        inputs:
          command: 'publish'
          publishWebProjects: true
          arguments: '--output "$(Build.ArtifactStagingDirectory)"'

      - task: sbom-tool@1
        displayName: 'Generate project SBOM manifest'
        inputs:
          command: 'generate'
          buildSourcePath: '$(Build.SourcesDirectory)'
          buildArtifactPath: '$(Build.ArtifactStagingDirectory)'
          enableManifestSpreadsheetGeneration: true
          enableManifestGraphGeneration: true
          enablePackageMetadataParsing: true
          fetchLicenseInformation: true
          fetchSecurityAdvisories: true
          gitHubConnection: 'GitHub Advisory Database Connection'
          packageSupplier: 'MyOrganisation'
          packageName: 'MyPackage'
          packageVersion: '$(Build.BuildNumber)'

      - task: PublishBuildArtifacts@1
        displayName: 'Publish artifacts'
        inputs:
          PathtoPublish: '$(Build.ArtifactStagingDirectory)'
          ArtifactName: 'drop'
          publishLocation: 'Container'
```

The SBOM manifest files will be uploaded to the build artifacts, under the `_manifest` folder.

![example.build.artifacts.png](images/example.build.artifacts.png)

### Importing an SBOM generated by another tool

If you already generate an SPDX manifest with a different tool (e.g. syft, trivy, or a previous
pipeline run) and just want to view/enrich it with this extension's "SBOM" report tab, use
`command: 'import'` instead of `generate` — it attaches the existing file directly, without running
`sbom-tool` at all:

```yaml
- task: sbom-tool@1
  displayName: 'Import SBOM manifest'
  inputs:
    command: 'import'
    importManifestFilePath: '$(Pipeline.Workspace)/**/*.spdx.json'
    enableManifestSpreadsheetGeneration: true
    fetchSecurityAdvisories: true
    gitHubConnection: 'GitHub Advisory Database Connection'
```

### Supplying vulnerability data from another scanner

`fetchSecurityAdvisories` only supports GitHub connections authenticated via OAuth or a personal
access token. If your GitHub connection uses another auth scheme (e.g. a GitHub App installation
token), or your vulnerability data comes from another scanner entirely (Trivy, `npm audit`,
`dotnet list package --vulnerable`, etc), use `vulnerabilitiesSource` instead (or alongside)
`fetchSecurityAdvisories` — it points to one or more local JSON files describing vulnerabilities to
attach to the SBOM:

```yaml
- task: sbom-tool@1
  displayName: 'Import SBOM manifest'
  inputs:
    command: 'import'
    importManifestFilePath: '$(Pipeline.Workspace)/**/*.spdx.json'
    vulnerabilitiesSource: '$(Pipeline.Workspace)/**/*.vulnerabilities.json'
```

Each referenced file must contain a JSON array of vulnerabilities in the following shape:

```jsonc
[
  {
    "packageName": "left-pad", // Required; matched case-insensitively against SBOM package names
    "packageVersion": "1.3.0", // Optional; if omitted, matches the package regardless of version
    "id": "GHSA-xxxx-xxxx-xxxx", // Required; GHSA id, CVE id, or any other identifier from your scanner
    "cveId": "CVE-2021-24112", // Optional
    "severity": "CRITICAL", // Required; one of LOW, MODERATE, HIGH, CRITICAL
    "summary": "One-line title", // Optional
    "description": "Longer free-text description", // Optional
    "url": "https://github.com/advisories/GHSA-xxxx-xxxx-xxxx", // Optional; a link is derived from id/cveId if omitted
    "vulnerableVersionRange": "< 5.0.2", // Optional
    "fixedVersion": "5.0.2", // Optional
    "cvssScore": 9.8, // Optional
    "publishedAt": "2021-03-01T00:00:00Z", // Optional
  },
]
```

Matched packages are enriched with the same security advisory external references that
`fetchSecurityAdvisories` would have added, so they appear identically in the "SBOM" report tab.

A formal [JSON Schema](docs/schemas/vulnerabilities-source.schema.json) and
[example file](docs/schemas/vulnerabilities-source.example.json) are available if you want to
validate your generated file before feeding it to the task, e.g. with
[`ajv`](https://ajv.js.org/):

```bash
node -e "
const Ajv2020 = require('ajv/dist/2020');
const validate = new Ajv2020({ strict: false, validateFormats: false }).compile(require('./docs/schemas/vulnerabilities-source.schema.json'));
const valid = validate(require('./my-report.json'));
console.log(valid ? 'valid' : JSON.stringify(validate.errors, null, 2));
"
```

The document root is a JSON array, so it can't carry an inline `"$schema"` property; in VS Code,
associate it instead via the `json.schemas` setting (`fileMatch` + the schema's raw GitHub URL, from
its `$id` field).
